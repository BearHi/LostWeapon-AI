# LostWeapon Native Physics Playground

## 실행

`dist/LostWeapon_Native_Playground.exe`를 더블클릭한다. 처음에는 훈1 원본 상태를 읽고 원본 Client x86 월드를 구성하므로 창 안에 맵이 나타날 때까지 몇 초 기다린다.

## 조작

- 방향키: 이동, 점프, 구르기 조합 입력
- C: 낙하산
- Z / X: 행동 입력
- Space: 재생/일시정지
- 위쪽 맵 선택: 훈1~훈20 및 6.5/7.5/8.5 불러오기
- `LMF 열기...`: 훈 시리즈 밖의 원하는 `.LMF` 직접 불러오기
- `1틱`: 정지 상태에서 정확히 한 틱 실행
- `미세 1틱` 줄: 무입력/방향/대각 조합/C/Z를 정확히 한 게임 틱만 실행하고 자동 일시정지
- 1~4: 무기 슬롯 선택, Z: 선택한 무기로 공격
- `상태 저장` / `복원`: 같은 시작 상태에서 다른 입력을 시험
- 속도: 1/2/4/8배 실행. 물리는 별도 프로세스에서 돌고 화면은 30fps로 갱신하므로 키와 창 조작이 물리 실행을 막지 않는다. 1배 재생은 정상 Client의 실제 걷기 경계에서 측정한 약 16ms/tick(62.5 tick/s)에 맞춘다.

## 현재 화면의 의미

화면은 시험용 렌더러다. 정적 맵 타일은 LMFeditor에서 추출한 원본 BMP 아이콘으로 표시하며, 들락가시와 사라지는 블록은 원본 런타임 상태에 맞춰 갱신한다. 캐릭터 이동, 충돌, 오브젝트 업데이트, 입력 상태는 캡처한 원본 Client 상태와 원본 Client x86 함수로 계산한다. 원본 DirectDraw 렌더러와 메뉴, 온라인 기능은 아직 포함하지 않았다. Space는 기지 입력에 사용하므로 재생/일시정지 단축키는 F5다.

평소 1x 재생은 실제 Client 장거리 측정값인 62.5 tick/s에 맞춘다. 훈1에서 240px 이동의 59개 틱 간격은 실제 Client 944.8ms(62.45Hz)였다. 에뮬레이트한 `timeGetTime`도 실제 측정에 맞춰 틱당 16ms 증가시켜 이동과 시간 기반 기믹이 같은 시계를 사용한다. `상태 저장`을 누른 뒤에는 복원을 위해 페이지 추적이 켜지므로 복잡한 맵에서 화면 재생이 느려질 수 있다. 다시 `초기화`하면 빠른 재생 상태로 맵을 다시 불러온다.

1x 화면도 이전 30 FPS 제한을 제거해 원본 물리 이벤트마다 최대 62.5회 갱신한다. 4x 이상에서는 오래된 화면 이벤트가 입력보다 늦게 처리되지 않도록 물리는 전부 실행하되 표시용 상태만 최신 경계로 줄여 보낸다.

`맵테스트2`처럼 raw51 장치가 수백 개 있는 세로 맵은 원본 dispatcher가 먼 장치까지 매 틱 순회해 41~59 tick/s로 떨어졌다. raw51은 원본 type-270의 지역 overlap 장치이므로 플레이어 반경 8칸의 원본 런타임 레코드만 dispatcher에 넣도록 했다. 이 맵의 활성 목록은 549개에서 159개로 줄었고, 사용자가 실제로 수행한 두 번의 점프/뒷굴 입력을 포함한 2,000틱을 전후 방식으로 재생했을 때 모든 player state와 SHA-256이 일치했다. 단독 처리량은 58.97에서 102.79 tick/s로 올랐고 GUI를 함께 그릴 때도 62.53 tick/s를 유지했다.

2026-09-15 동시 키보드 재검사에서는 양쪽 위치/상태가 tick 150까지 같은 경계를 반복해서 만들었지만, LEFT+RIGHT에서 RIGHT 단독으로 바뀌는 물리 경계에서 갈렸다. 오라클은 tick 150 `(204,12554.4)` 다음에 RIGHT를 적용해 tick 151 `(208,12548.8)`이 되었고, normal Client는 같은 벽시각에 이미 물리 계산을 마친 `(200,12549.2)` 상태를 노출한 뒤 다음 경계에서 새 키를 반영했다. 두 프로세스의 62.5 Hz 위상이 독립적이므로 OS 키 상태를 동시에 받는 것만으로 동일 tick action sequence가 보장되지 않는다. 이 차이가 발판/자석 경계에서 누적되어 경로가 크게 갈렸다. 이는 컴퓨터 처리량 저하 증거가 아니며, 학습 API처럼 action을 tick에 직접 지정하는 실행에는 해당하지 않는다. 화면 parity 검증은 normal Client 경계에서 관측한 입력열을 offline oracle에 replay해야 한다. Evidence: `evidence/maptest2_simultaneous_input_phase_diagnosis.json`.

두 프로그램에 물리 틱 수가 같아도 키를 누르는 순간이 각 프로그램의 틱 경계 앞뒤로 갈리면 점프/구르기 press edge가 한 틱 다를 수 있다. 여유가 거의 없는 발판에서는 이 한 틱만으로 결과가 갈릴 수 있으므로, 엄밀한 parity 판정은 실제 Client 입력 trace를 같은 tick sequence로 oracle에 재생해서 한다.

현재 정상 Client와 틱 단위로 확인한 범위는 기본 이동/점프/구르기/낙하산, 사다리, 물, 스프링, 선풍기, 네 방향 자석, 두 종류 얼음, 사라지는 블록이다. 실행 파일 자체 진단은 훈1 RIGHT 12틱 `x 112 -> 160`과 저장/복원 후 전체 상태열의 정확한 재현을 검사한다.

화면 위 상태줄은 좌표를 소수점 셋째 자리까지 표시하고 현재 무기 슬롯, 앉기, 낙하산, 앞굴/뒷굴, 공격, 물속 상태와 얼음 관성값을 함께 표시한다. 앉기 때 화면의 캐릭터 사각형 높이도 줄어든다. 충돌 판정 자체는 계속 원본 x86이 계산한다.

피격 상태 `state38=5` 또는 유효한 보호/피격 코드가 유지되는 동안은 `피격/누움`으로 표시한다. 불(raw48)은 실제로 `state38=5, +0x7c=12`를 쓰므로 5/7만 검사하면 누움을 놓친다. 원본 x86에서 불 피격 뒤 가시 접촉 16틱과 가시 단독 피격 뒤 12틱 모두 새 피격 없이 기존 누움 상태가 유지되는 회귀검사를 통과했다. 공격 중에는 원본 Client가 현재 프레임에 계산한 판정 경계를 주황색 점선으로 표시하며, 공격이 끝나면 즉시 숨긴다.

장시간 재생에서 Unicorn 번역 캐시가 계속 늘던 문제를 막기 위해 1,024틱마다 번역 캐시만 비운다. emulated 메모리와 CPU 상태에는 손대지 않는다. 훈1 NOOP 20,000틱에서 runtime object count는 11로 고정됐고 private memory 증가는 32.39MB에서 1.32MB로 줄었으며 572.5 tick/s를 유지했다.

하늘색 고리 위에 검은 돌이 놓인 접촉 지뢰는 LMF raw43이며 원본 runtime type은 290(`0x122`)이다. 이 레코드를 정적 grid writer로 오인해 dispatcher에서 제거하면 그림과 collision grid는 남아도 접촉 피격이 사라진다. raw43 runtime record를 유지하고 필요한 `SetRect` 환경 호출을 구현한 뒤, 자석낙라1의 raw43 `(3,12)` 접촉 첫 tick에 원본 피격 코드 `+0x7c=5`가 재현됐다. raw51 선풍기, raw63 동전블록, raw87/88 폭발물과 구분한다.

현재 맵의 매 tick 입력/좌표/상태/얼음 관성은 `evidence/playground_recent_trace.jsonl`에 자동 기록된다. 이상 동작이 나온 직후 맵 이름만 알려주면 사용자가 키 순서를 다시 외워 적지 않아도 해당 구간을 역추적할 수 있다. 새 맵을 불러오면 기록은 그 맵 기준으로 초기화된다.

맵 시작은 ID 100 위치에서 시작한다. 발밑이 비어 있으면 첫 중력 틱부터 떨어진다. 훈12도 시작점 아래 물로 자연스럽게 낙하한다.

원본 빌더가 오브젝트를 만들지 않는 에디터 제어 레코드도 누적 개수를 x86 배치 안에서 추적하도록 고쳤다. 이 때문에 실패하던 `맵테스트2`, `맵테스트5`를 포함해 `맵테스트1~10`, `맵테스트55`, `맵테스트66`이 모두 로드와 원본 world tick을 통과한다.

큰 맵의 타일은 한 장의 비트맵으로 합쳐 표시한다. 정적인 벽/장식은 원본 collision grid를 유지한 채 dispatcher 목록에서 빼고, 사다리/경사는 원본 `0x42ed50`을 한 x86 배치로 실행한다. 상태가 없는 용암은 플레이어 주변 6칸의 원본 런타임 레코드만 활성화한다. 전체 목록과 비교한 용암 접촉·사망·리스폰 40틱과 저장/복원 분기가 정확히 일치했다. `맵테스트5`는 약 25→101 tick/s, `맵테스트6`은 약 27→214 tick/s로 측정됐다. 이 검증은 해당 경로의 결과이며 모든 미검증 기믹 조합에 대한 parity 증명은 아니다.

공간 최적화가 맵 오브젝트 목록을 다시 만들 때 공격·지뢰처럼 실행 중 추가된 Client 오브젝트를 잃지 않도록 원본 레코드 전체를 함께 보존한다. 두 차례 연속 공간 갱신 뒤에도 임시 오브젝트의 타입·범위 바이트가 그대로 남는 회귀 검사가 있다.

커스텀 LMF를 로드할 때 원본 `0x46c690`이 설정하는 grid geometry metadata도 함께 갱신한다. 이전에는 훈1 캡처의 `30x18` 픽셀 경계가 남아 있어 넓은 맵에서 얼음 관성이 `x=960-48=912`에 고정됐다. 낙라의 동일 입력 기록을 정지 직전까지 재생한 뒤 실제 `65x65` 경계를 적용한 검증에서는 `912→916→920→924`로 계속 이동했다. `tests/map_geometry_regression.py`가 타일 크기와 원본 코드용 픽셀 경계의 동기화를 검사한다.

## 파일 배치

실행 파일은 `native_harness/dist` 안에서 사용한다. 이 실행기는 같은 프로젝트의 `native_playground.py`, `private_snapshots`, `훈련용맵`을 읽는다.
