내 판단은 **지금 막힌 주원인은 9×9가 어렵거나 훈련량이 부족해서가 아니라, 이미 만든 물리를 행동 선택에 제대로 활용하지 않는 구조**야.

붙여준 두 채팅과 인계·감사 문서, 현재 훈련기와 실시간 헬퍼 코드를 대조했어. 코드 수정과 훈련 실행은 하지 않았어.

**1. 지금 무엇이 문제인가**

가장 큰 문제는 **읽은 정보와 실제 판단에 쓰는 정보가 다르다**는 거야.

현재 [훈련기의 상황 표현](<./native_harness/train_rule_helper.py:50>)은 사실상 이 다섯 개야.

> 목표가 좌/우인가 · 목표가 위/아래인가 · 바로 앞 공간 · 두 칸 앞 바닥 · 일반/사다리/물/낙하산 상태

여기에는 속도, 바라보는 방향, 칸 안에서의 정확한 위치, 구르기 진행 상태, 무기, 용암 폭 같은 정보가 없어.

그러면 **발판 중앙에서 오른쪽으로 움직이는 상황과, 발판 끝에서 반대쪽을 보며 떨어지는 상황을 같은 상황으로 배울 수 있어.** 한쪽에서는 성공한 입력이 다른 쪽에서는 실패하니, 계속 훈련해도 행동값이 뒤섞여.

추가로 확인한 문제는 이래.

| 문제 | 실제 영향 |
|---|---|
| 이동 후보가 행동 번호 0~11로 제한됨 | C는 포함되지만 Z·무기 선택은 제외돼. 장검을 이용한 이동 해법을 발견할 수 없어. |
| 짧은 키 입력을 고르고, 연속 기술을 미리 비교하지 않음 | 뒷굴→낙하산의 최종 착지 결과를 보고 뒷굴을 선택하는 구조가 없어. |
| 깃발 방향 가산점과 거리 개선에 의존 | 먼저 반대로 가야 하는 우회로를 선택하기 불리해. |
| 실시간 헬퍼가 별도의 지형 규칙을 추가함 | 훈련에서 얻은 선택과 실제 플레이의 선택이 달라질 수 있어. |
| 성공 경로 재생과 독립 판단의 성적이 섞임 | 기록을 잘 재생하는 것과 새로운 상황을 해결하는 것을 구분하기 어려워. |

또 현재 학습은 과거 결과를 평균내는 방식이야. **서로 다른 상황을 같은 항목으로 합쳐 놓고 평균을 더 정확히 계산해도, 필요한 구분은 생기지 않아.**

대화에서 반복된 개발상의 문제도 분명해. 요구 전체를 고정한 뒤 연결 여부를 검사하지 않고, “뒷굴이 빠졌네 → 뒷굴 추가”, “Z가 빠졌네 → Z 추가”로 대응했어. 그래서 네가 매번 빠진 요구를 다시 찾아줘야 했던 거야.

**2. 9×9는 유지해도 된다. 다만 두뇌 전체를 9×9에 가두면 안 돼**

나는 **9×9를 기본 근거리 관측으로 유지**하는 쪽이 맞다고 봐. 지금 4×4로 줄일 이유는 없어. 필요한 착지점과 장애물이 더 안 보일 수 있으니까.

대신 정보를 이렇게 나눠야 해.

- **주변 9×9:** 당장 부딪힐 벽, 발판 끝, 용암, 기술을 시작할 공간.
- **발견한 지도 전체:** 깃발까지 어느 발판·사다리·통로를 거칠지.
- **캐릭터 상태:** 정확한 위치·속도·방향·동작 단계·무기·입력 유지 상태.
- **상대 정보:** 미니맵 위치, 마지막 관측 시각, 접근 가능 방향.

그리고 시야 확대 기준은 “학습이 안 되면 한 칸 확대”보다 **“시험하려는 기술의 궤적과 착지점이 시야 밖이면 그쪽을 확인”**하는 게 좋아.

9×9 밖에 착지하는 기술을 평가하는데 끝까지 9×9만 보면, 정보가 없어서 판단할 수 없는 상황이 생겨. 이건 지능이나 훈련량으로 해결되지 않아.

**3. 내가 잡을 구조는 ‘길 선택 → 기술 비교 → 실행 → 결과 확인’이야**

| 부분 | 맡길 일 |
|---|---|
| 상태·지도 관리 | 현재 물리 상태와 발견 지형을 보존한다. 모르는 곳은 모르는 상태로 둔다. |
| 큰 경로 계획 | 깃발까지 거칠 발판·통로를 정하고, 다음 중간 목표를 준다. |
| 기술 후보 생성 | 걷기·점프·앞굴·뒷굴·C·Z·무기 전환을 상태에 맞게 조합한다. |
| 물리 예측 | 현재 상태에서 후보를 시험해 궤적·착지·시간·복귀 여부를 비교한다. |
| 실행 제어 | 선택한 기술을 수행하되 예상에서 벗어나면 수정한다. 수동 조작에는 즉시 양보한다. |
| 학습 | 유망한 후보와 타이밍을 먼저 찾도록 개선하고, 성공·실패 경험을 재사용한다. |

여기서 **기술은 고정된 키 배열만을 뜻하면 안 돼.**

예를 들어 `뒷굴 → 낙하산`은 “몇 프레임 뒤 무조건 C”가 아니라, **뒷굴을 시작하고, 원본 상태가 낙하산을 펼칠 수 있는 상태가 됐을 때 C를 입력하는 동작**이어야 해. 시작 조건·진행 중 판단·종료 조건이 있어야 다른 위치에서도 재사용할 수 있어. 이런 시간에 걸친 행동을 학습 단위로 삼는 접근은 기존 연구에도 있어. [기술 단위 행동 연구](https://www.sciencedirect.com/science/article/pii/S0004370299000521)

네가 말한 3칸 용암이면 판단은 이렇게 해야 해.

> 건너편 착지 구간 지정
> → 현재 방향·속도에서 가능한 기술 조합 생성
> → 뒷굴, 뒷굴→C, 점프→앞굴, 장검 연계 등의 실제 결과 비교
> → 시작 지역 복귀 없이 착지하고 다음 이동까지 이어지는 후보 선택

**“용암이면 점프” 같은 지형별 정답 규칙을 계속 늘릴 필요는 없어.** 기술의 실행 조건과 물리 결과를 이용해 조합해야 해.

다만 “물리를 알면 무조건 즉시 정답”까지는 아니야. 모든 입력과 타이밍을 끝없이 조합하면 계산량이 커져. 그래서 **기존 성공 기술부터 시험하고, 유망한 후보만 더 이어 보며, 짧게 실행한 뒤 다시 판단**해야 해. 이 재계획 방식은 모델 예측 제어와 같은 방향이야. [MIT 설명](https://underactuated.mit.edu/trajopt.html)

**4. 보상과 학습은 유지하되, 맡길 문제를 바꿔야 해**

이미 원본 물리로 결과를 계산할 수 있다면, 걷기부터 무작위로 다시 발견시키는 데 훈련 대부분을 쓸 이유는 적어.

학습에는 이런 일을 맡기겠어.

- 이 상태에서 **어느 기술을 먼저 시험하면 좋은지**.
- 기술 시작 위치와 입력 타이밍을 어떻게 바꾸면 더 안정적이고 빠른지.
- 기존 성공 구간을 지금 상황에 재사용할 수 있는지.
- 짧은 예측 끝에서 어느 상태가 이후 깃발 도달에 유리한지.

보상은 깃발 도달·시간 단축을 중심으로 유지하고, 용암 접촉 자체는 실패로 취급하지 않아. 네 요구대로 **위험 접촉 때문에 처음으로 돌아가 진행을 잃은 결과**를 구분해야 해. 명중·회피는 전투를 연결한 뒤 보조 목표로 넣고.

기존 성공·실패 기록도 쓸모가 있어. 성공열은 기술 후보와 개선 출발점으로, 실패열은 적용 조건을 찾는 자료로 써야 해. 다만 **현재의 정보가 부족한 행동값 표를 그대로 새 두뇌의 정답으로 삼는 건 피해야 해.**

**5. 앞으로는 이 순서로 진행하는 게 맞아**

1. **기존 물리를 판단기에 쓸 수 있는지 연결 상태부터 확인.**
   같은 시작 상태를 복제해 후보 A와 B를 공정하게 비교할 수 있는지, 필요한 동작 상태가 보존되는지, 얼마나 빨리 예측되는지 확인해. 물리 전체를 처음부터 다시 만들자는 뜻은 아니야.

2. **한 장애물에서 ‘설명 가능한 선택’을 먼저 완성.**
   네 3칸 용암 사례가 적합해. 후보별 실패 이유·착지 위치·소요 시간과 선택 이유가 나와야 해. 한 가지 성공 입력열만 찾고 끝내면 안 돼.

3. **같은 장애물의 시작 위치·방향·속도를 바꿔 확인.**
   여기서 적응해야 상황을 보고 판단하는 헬퍼라고 볼 수 있어.

4. **발판 사이 이동을 연결해 깃발 경로를 완성.**
   깃발에서 잠깐 멀어지는 우회도 선택할 수 있어야 해.

5. **동일한 판단기를 훈련과 실시간에 사용하고, 이후 전투를 연결.**
   실시간용으로 별도의 간이 두뇌를 다시 만들면 지금 문제가 반복돼.

실패했을 때도 “더 돌려보자” 전에 **해법이 후보에 없었는지 → 예측이 틀렸는지 → 비교 점수가 틀렸는지 → 실제 입력 타이밍이 틀렸는지**를 나눠야 해. 원인마다 고칠 부분이 달라.

- [자동 자료 수집](<./native_harness/이번주_자료수집.bat>): 짧은 행동 실험만 최대 1시간. 반복 실행 가능하고 누적량 제한도 넣었어.
- [중지](<./native_harness/이번주_중지.bat>) / [결과 정리](<./native_harness/이번주_결과정리.bat>)

둘 다 로컬 실행이라 API 토큰은 쓰지 않아. 다음 주에는 자동 저장된 요약과 기록을 보면 돼.

설계 방향은 **사람 시범 → 짧은 기술 학습 → 다시 관측해서 행동 수정 → 방문 지형 기억**이야. 시범을 학습에 연결하는 단계는 아직 남았어. 관련 테스트 24개는 통과했지만, 새 기록 기능의 실제 게임 동작은 첫 사용에서 확인해야 해.
